\## 1.2 项目定位



本项目不是训练一个新的大语言模型，也不是简单开发一个普通聊天机器人。



我们真正需要构建的是一个位于多个大模型之前的：



> \*\*智能模型路由与网管系统（Intelligent Model Router）\*\*



企业在实际使用大模型时，可能同时拥有多个能力、成本和响应速度不同的大模型。



当一个新的用户请求到达时，我们的系统需要自动判断：



> \*\*这一次请求究竟应该交给哪一个模型处理？\*\*



最终目标是在首先保障回答质量的前提下：



1\. 尽可能降低大模型调用成本；

2\. 进一步降低响应时延；

3\. 提高多模型服务集群的整体资源利用效率。



可以将本项目简单理解为：



> \*\*多个大模型之前的“智能调度层”。\*\*

\# 2. 项目背景与问题定义



\## 2.1 为什么需要模型路由



随着大模型逐渐应用于企业知识问答、代码生成、数据分析、智能客服、内容生成等场景，企业通常不会只使用单一模型，而是可能同时接入多个不同的大模型。



例如一个模型池中可能包含：



\- 能力很强，但价格较高、响应较慢的模型；

\- 编程能力较强的模型；

\- 数学和逻辑推理能力较强的模型；

\- 中文问答效果较好的模型；

\- 能力相对有限，但价格低、响应速度快的小模型。



不同模型在不同任务上具有不同优势。



因此：



> \*\*并不是所有请求都有必要调用最强、最贵的模型。\*\*



例如，一个简单的文本摘要任务可能使用轻量模型就已经能够达到较好的效果。如果仍然调用高成本模型，就会产生没有必要的资源和费用消耗。



反过来，对于复杂推理、代码分析等任务，如果为了降低成本而选择能力不足的模型，则可能导致回答质量无法满足要求。



因此，企业需要一种能够自动在多个模型之间进行选择和调度的机制。



\---



\## 2.2 传统方案的问题



\### 方案一：所有请求固定调用最强模型



优点：



\- 实现简单；

\- 通常具有较高回答质量。



问题：



\- 调用成本高；

\- 对简单任务存在明显资源浪费；

\- 强模型通常响应时间也更长。



\---



\### 方案二：所有请求固定调用最低成本模型



优点：



\- 成本低；

\- 通常响应较快。



问题：



\- 复杂任务质量可能明显不足；

\- 无法满足高质量服务要求。



\---



\### 方案三：人工规则路由



例如：



&#x20;   编程任务 → Model A

&#x20;   数学任务 → Model B

&#x20;   文本摘要 → Model C



这种方法比固定模型更加合理，但仍然存在：



\- 路由规则依赖人工设计；

\- 规则需要持续人工维护；

\- 无法充分利用历史运行数据；

\- 很难适应请求类型分布变化；

\- 无法根据不同模型真实运行表现动态调整。



\---



\## 2.3 我们需要解决的问题



本项目希望利用历史请求数据，让 Router 自动学习：



> \*\*什么样的请求更加适合交给什么模型处理。\*\*



针对每一个新的用户请求，系统需要综合考虑：



\- 请求内容；

\- 请求所属任务类型；

\- 请求复杂程度；

\- 不同模型历史响应质量；

\- 不同模型调用成本；

\- 不同模型服务时延；

\- 模型擅长的任务类型；

\- 后续可扩展的模型实时运行状态。



最终选择当前最合适的模型。



命题规定的核心优化目标具有明确优先级：



1\. \*\*首先保证模型响应质量达到用户要求；\*\*

2\. \*\*在质量达标的模型中优先降低调用成本；\*\*

3\. \*\*在质量和成本相近的情况下进一步降低响应时延。\*\*



因此，本项目本质上可以理解为一个：



> \*\*历史数据驱动的模型性能预测 + 约束决策 + 动态资源调度问题。\*\*



\---



\# 3. 我们最终要做什么



最终希望形成一个完整的大模型智能网管软件系统。



系统的整体工作链路可以表示为：



&#x20;   用户提交 Query

&#x20;         ↓

&#x20;   请求特征分析

&#x20;         ↓

&#x20;   预测不同模型处理该请求的效果

&#x20;         ↓

&#x20;   智能 Router 进行决策

&#x20;         ↓

&#x20;   选择最合适的大模型

&#x20;         ↓

&#x20;   调用目标模型

&#x20;         ↓

&#x20;   返回模型响应

&#x20;         ↓

&#x20;   记录实际质量 / 成本 / 时延

&#x20;         ↓

&#x20;   写入历史数据

&#x20;         ↓

&#x20;   用于后续 Router 优化



系统本身不替代任何一个大模型，而是负责管理和调度多个已有模型。



逻辑结构可以理解为：



&#x20;                        ┌── Model A

&#x20;                        │

&#x20;   用户请求 → Zhiheng Router ── Model B

&#x20;                        │

&#x20;                        ├── Model C

&#x20;                        │

&#x20;                        └── Model D ...



Router 最核心的任务就是完成：



&#x20;   query\_new → model\*



也就是：



> \*\*给定一个新的用户请求，输出当前最合适的目标模型。\*\*

\# 4. 核心实现路径



项目整体初步分为以下几个主要技术步骤。



\---



\## 4.1 历史数据构建



华为命题给出的历史请求数据可以抽象为：



&#x20;   D = {

&#x20;       query\_i,

&#x20;       model\_j,

&#x20;       quality\_score\_i,

&#x20;       latency\_i,

&#x20;       cost\_i

&#x20;   }



也就是说，每一条历史记录至少包含：



\- 用户请求 Query；

\- 实际调用模型 Model；

\- 模型响应质量 Quality；

\- 实际响应时延 Latency；

\- 调用成本 Cost。



例如：



| Query | Model | Quality | Latency | Cost |

|---|---|---:|---:|---:|

| 编写 Python 快速排序 | Model A | 0.94 | 2.1 s | 0.08 |

| 编写 Python 快速排序 | Model B | 0.91 | 1.3 s | 0.03 |

| 简单文本摘要 | Model C | 0.88 | 0.7 s | 0.01 |



通过大量类似历史记录，可以逐渐获得：



> \*\*不同模型在不同类型任务上的性能画像。\*\*



这些历史数据将成为 Router 学习和决策的基础。



\---



\## 4.2 请求特征提取



用户提交的 Query 本质上是一段自然语言文本。



Router 不能简单依赖原始文本直接决策，因此需要首先把 Query 转化为能够供算法使用的特征。



候选特征主要包括以下几类。



\### 基础文本特征



例如：



\- Query 长度；

\- Token 数量；

\- 是否包含代码；

\- 是否包含大量数字；

\- 是否包含数学公式；

\- 是否要求结构化输出。



\### 任务类型特征



例如：



\- 编程；

\- 数学；

\- 推理；

\- 摘要；

\- 翻译；

\- 知识问答；

\- 信息抽取；

\- 内容生成。



\### 任务复杂度



可以尝试划分为：



\- 简单；

\- 中等；

\- 困难。



\### 语义特征



后续可以利用：



\- Embedding；

\- 小型文本编码模型；



把 Query 转换为语义向量。



整体流程为：



&#x20;   Query

&#x20;     ↓

&#x20;   Feature Extractor

&#x20;     ↓

&#x20;   Request Feature Vector



\---



\## 4.3 模型性能估计



这是整个系统的关键步骤之一。



当一个新的 Query 到达时，我们并不知道：



\- Model A 回答这道题质量是多少；

\- Model B 回答效果怎么样；

\- Model C 是否更加适合；

\- 哪个模型会更快。



如果为了判断效果而把同一个 Query 同时发送给所有模型，再根据结果决定选择哪个模型，那么路由本身就失去了实际意义，因为成本和时间已经全部产生。



因此，需要根据历史数据提前估计：



&#x20;   Expected Quality

&#x20;   Expected Latency

&#x20;   Expected Cost



例如对于某个新 Query：



| Model | Predicted Quality | Cost | Predicted Latency |

|---|---:|---:|---:|

| Model A | 0.95 | 0.10 | 2.8 s |

| Model B | 0.91 | 0.03 | 1.4 s |

| Model C | 0.84 | 0.01 | 0.8 s |

| Model D | 0.72 | 0.005 | 0.5 s |



通过这一模块，Router 可以在真正调用模型之前大致判断：



> \*\*每个候选模型处理当前请求时可能达到什么效果。\*\*



\---



\## 4.4 Router 路由决策



假设当前用户要求：



&#x20;   Quality ≥ 0.80



那么根据上述预测：



Model D 的预测质量：



&#x20;   0.72 < 0.80



因此 Model D 不满足质量要求，直接从候选模型中排除。



剩余：



&#x20;   Model A

&#x20;   Model B

&#x20;   Model C



都满足质量要求。



接下来比较成本：



&#x20;   Model A：0.10

&#x20;   Model B：0.03

&#x20;   Model C：0.01



那么 Router 会优先选择：



&#x20;   Model C



因为它已经满足质量要求，同时调用成本最低。



如果多个模型成本接近，则进一步比较响应时延。



整个核心决策流程可以表示为：



&#x20;   所有候选模型

&#x20;         ↓

&#x20;   预测各模型响应质量

&#x20;         ↓

&#x20;   过滤质量不达标模型

&#x20;         ↓

&#x20;   比较调用成本

&#x20;         ↓

&#x20;   比较响应时延

&#x20;         ↓

&#x20;   选择最终 model\*



\---



\## 4.5 模型调用



Router 完成模型选择之后，需要通过统一接口调用目标大模型。



未来系统内部可以设计成：



&#x20;   Zhiheng Router

&#x20;         │

&#x20;         ├── Model A API

&#x20;         ├── Model B API

&#x20;         ├── Model C API

&#x20;         ├── Model D API

&#x20;         └── ...



不同模型在系统内部尽量使用统一的 Model Adapter 管理。



理想调用方式类似：



&#x20;   call\_model(model\_id, query)



这样未来更换或者增加模型时，不需要修改 Router 本身的主要逻辑。



\---



\## 4.6 结果记录与历史反馈



目标模型返回响应后，系统继续记录：



\- Query；

\- Selected Model；

\- Actual Quality；

\- Actual Cost；

\- Actual Latency。



这些新数据重新进入历史数据库。



后续可以进一步形成：



&#x20;   历史数据

&#x20;      ↓

&#x20;   Router Training

&#x20;      ↓

&#x20;   Routing

&#x20;      ↓

&#x20;   Real Feedback

&#x20;      ↓

&#x20;   New Historical Data

&#x20;      ↓

&#x20;   Router Update



从而形成一个持续优化的闭环。



需要注意：



> \*\*在线持续学习目前不是命题明确规定的第一阶段硬性要求，因此现阶段将其作为后续增强能力，而不是 MVP 必须功能。\*\*

\# 5. 初步技术方案



目前项目处于早期阶段，因此最终 Router 算法暂时不完全锁定。



当前技术原则为：



> \*\*首先建立简单、可靠、可测试的系统，再逐步增加算法复杂度。\*\*



\---



\## 5.1 Baseline



在开发智能 Router 之前，需要首先建立若干基线方法。



这样后续才能回答：



> \*\*我们的 Router 到底有没有真正带来提升？\*\*



\### Baseline 1：Strongest Model



所有请求固定发送给能力最强的大模型。



目的：



观察完全不考虑成本时能够获得怎样的质量表现。



\---



\### Baseline 2：Lowest Cost Model



所有请求固定发送给调用成本最低的大模型。



目的：



观察极端追求低成本情况下会损失多少质量。



\---



\### Baseline 3：Rule-based Router



通过人工规则完成路由。



例如：



&#x20;   Coding → Model A

&#x20;   Math → Model B

&#x20;   Summary → Model C



用于代表传统固定规则路由方法。



\---



\## 5.2 智能 Router V1



第一版 Router 暂时不追求复杂算法。



初步思路：



&#x20;   Query

&#x20;     ↓

&#x20;   Feature Extraction

&#x20;     ↓

&#x20;   Lightweight Prediction Model

&#x20;     ↓

&#x20;   Model Performance Prediction

&#x20;     ↓

&#x20;   Quality Constraint

&#x20;     ↓

&#x20;   Cost / Latency Optimization

&#x20;     ↓

&#x20;   model\*



第一阶段候选算法可以包括：



\- Logistic Regression；

\- Random Forest；

\- XGBoost；

\- LightGBM；

\- 小型 MLP。



具体采用哪种方案，需要通过实验进行比较后确定。



\---



\## 5.3 后续可能研究的增强方案



在 Router MVP 和基础实验平台稳定以后，可以进一步尝试：



\- Contextual Bandit；

\- 在线学习；

\- 动态模型状态感知；

\- 不确定性感知；

\- 自适应质量阈值；

\- 多目标优化；

\- 历史反馈增量更新；

\- 强化学习 Router。



这些都是后续研究方向。



目前：



> \*\*不默认必须采用，也不为了技术复杂度而强行加入。\*\*



任何新增方法必须能够通过实验说明其实际价值。



\---



\## 5.4 评价指标



项目至少需要建立以下评价指标。



\### 质量指标



\- Quality Pass Rate；

\- Average Quality。



\### 成本指标



\- Average Cost；

\- Total Cost。



\### 时延指标



\- End-to-End Latency；

\- Router Latency。



\### 系统性能指标



\- Throughput；

\- QPS；

\- CPU Usage。



最终实验需要重点回答：



> \*\*智能 Router 是否能够在保证回答质量的情况下，相比固定模型和规则 Router 显著降低调用成本和响应时延？\*\*

\# 6. 系统组成



整个系统初步划分为以下几个主要模块。



\---



\## 6.1 数据模块



主要负责：



\- 历史请求数据读取；

\- 数据清洗；

\- 训练 / 测试数据划分；

\- 数据 Schema 管理；

\- 实验数据管理；

\- 后续反馈数据记录。



\---



\## 6.2 Feature 模块



负责：



&#x20;   Query → Features



主要可能包含：



\- Task Type；

\- Query Length；

\- Complexity；

\- Embedding；

\- Domain；

\- 其他任务相关特征。



\---



\## 6.3 Model Performance Predictor



负责预测不同模型处理当前 Query 时可能达到的：



&#x20;   P(Quality | Query, Model)



以及：



&#x20;   Latency(Query, Model)



Cost 在部分场景下可以直接由模型价格或者已有模型信息获得。



这一模块为 Router 决策提供依据。



\---



\## 6.4 Router



Router 是项目的核心算法模块。



输入：



&#x20;   Request Features

&#x20;         +

&#x20;   Model Performance



输出：



&#x20;   Routing Decision

&#x20;         ↓

&#x20;   Selected Model



Router 负责真正完成：



> \*\*哪个 Query 应该调用哪个模型。\*\*



\---



\## 6.5 Model Adapter



负责统一不同大模型的调用方式。



理想情况下使用统一接口：



&#x20;   call\_model(model\_id, query)



而不是在系统中到处出现：



&#x20;   if model == A:

&#x20;       ...

&#x20;   elif model == B:

&#x20;       ...



通过统一 Adapter，可以方便后续增加、删除或者替换模型。



\---



\## 6.6 Monitoring



主要负责记录：



\- 当前选择的模型；

\- 响应质量；

\- Cost；

\- Latency；

\- Router 推理时间；

\- 模型服务状态；

\- 累计调用统计。

\# 7. 项目阶段与里程碑



整个项目目前划分为五个主要阶段。



\---

\# 总结



本项目当前最重要的目标不是立即追求复杂算法，而是按照以下顺序稳步推进：



&#x20;   理解问题

&#x20;       ↓

&#x20;   设计系统

&#x20;       ↓

&#x20;   建立 Baseline

&#x20;       ↓

&#x20;   跑通 Router MVP

&#x20;       ↓

&#x20;   建立实验框架

&#x20;       ↓

&#x20;   验证智能路由有效性

&#x20;       ↓

&#x20;   系统工程化

&#x20;       ↓

&#x20;   鲲鹏部署与优化

&#x20;       ↓

&#x20;   形成完整竞赛作品



整个项目始终围绕一个核心问题展开：



> \*\*如何利用历史请求和模型性能数据，为每一个新请求动态选择最合适的大模型，在保障服务质量的同时降低模型调用成本与响应时延？\*\*



第一阶段最重要的是建立一个：



> \*\*可运行、可测试、可比较、可复现、可持续迭代\*\*



的模型路由系统。



所有后续算法优化、鲲鹏部署、系统工程化和竞赛展示工作，都将在这一基础上逐步完善。
